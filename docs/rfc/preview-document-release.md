# RFC: Release verified PDF versions in the local preview

**Status: Proposed.** Independent design slice for [#17](https://github.com/erp4us-org/erp4us/issues/17) / [DOC-001](../requirements/catalog/DOC.yaml) under [#119](https://github.com/erp4us-org/erp4us/issues/119) and [draft PR #120](https://github.com/erp4us-org/erp4us/pull/120). This is not implementation approval, a storage or license decision, or evidence that Documents or shipment works.

## Requirement and first example

An incomplete or unauthorized upload must never displace released evidence. In an agreement that allows split delivery, if NovaMotion dispatches six of the ten modules ordered by Atlas, the dispatch PDF must describe those six, not the confirmed order for ten. The remaining four have their own evidence; correcting the first PDF creates a new version without changing the original. The [execution proposal](novamotion-execution-preview.md) starts with a separate ship-complete scenario. A service-only engineering consultancy may retain a signed completion report under the same document invariant; it must not create a shipment or warehouse to attach it.

Prove the lifecycle first on a trusted, loopback-only installation with synthetic data and a server-seeded Documents fixture entity and eligibility list. That fixture cannot attest to fulfillment. Later, use a published, authorized contract of the fulfillment owner to resolve the [actual posted shipment snapshot](https://github.com/erp4us-org/erp4us/issues/51) (tenant, organization, shipment ID, immutable revision, posted line quantities and units). Persist the typed snapshot reference with the PDF version; generate from that snapshot and record `document_id` and `version` in process history, not a download grant. Do not accept arbitrary source IDs, client-supplied shipment facts, a plan, or an order as shipment evidence. No PDF generation, shipment workflow, OCR, classification, or real data in this slice.

## Proposed wire and authorization

Illustrative HTTP `/v1/documents` paths and fields (not an OpenAPI contract). Use bearer authentication and the existing `X-Erp4us-Tenant` and `X-Erp4us-Organization` selectors. Documents verifies issuer, audience, expiry, actor and membership; selectors only narrow verified scope. Every step checks the current operation grant and entity permission, against the server-seeded fixture for this slice. Include both scope dimensions in lookups and uniqueness constraints. Upload sessions and download grants are bound to the verified actor, including for service or agent callers; neither possession of an ID nor gateway access grants permission.

| Request (relative to `/v1/documents`) | Illustrative success |
|---|---|
| `POST /uploads` (`documents.upload.stage`): `command_id`, `entity: {kind, id}`, optional `document_id`, `expected_version` (0 for first release), `size_bytes`, `sha256` (64 lowercase hex digits), `media_type: "application/pdf"` | `201`: `upload_id`, `document_id`, `put_path`, `expires_at` |
| `PUT /uploads/{upload_id}/content` (`documents.upload.put`): one raw PDF body, `Content-Type: application/pdf` | `204`: bytes stored privately, nothing published |
| `POST /uploads/{upload_id}/finalize` (`documents.upload.finalize`): no body; the upload ID identifies the command | `200`: `document_id`, `version`, `size_bytes`, `sha256`, `media_type`, `released_at` |
| `POST /{document_id}/versions/{version}/download-grants` (`documents.version.read`): exact released version | `201`: `redeem_path`, opaque `grant`, `expires_at` |
| `POST /downloads/redeem` (`documents.version.read`): `{grant}` plus bearer and scope | `200`: exact PDF bytes; `Content-Type: application/pdf`, `Content-Disposition: attachment`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` |

Use UUID identifiers, monotonic versions and UTC RFC 3339 instants. Both paths returned to clients are same-origin Documents paths; the download grant goes in the redeem body, not in a URL. Redeem rechecks actor, scope, current grants, entity permission, expiry and exact released version. S3 is reachable only by Documents over private ingress, with bucket-scoped credentials and no anonymous access. Never return an S3 URL, key or credential; no redirects to storage. Redact grant bodies, authorization headers, raw links, object keys and PDF content from logs/traces at every hop. Keep access-controlled audit records of time, scoped actor, action, outcome, reason code and internal document/version reference where authorized, not content or credentials.

Illustrative errors: `401` for invalid authentication, `403` for a missing operation grant before lookup, indistinguishable `404` for absent or hidden resources, `409` for a stale expected version or already-written key, `413` over the cap, `422` for invalid content, and `503` for unavailable verification. Only the authorized, bound actor can receive `410` for an expired session or grant.

## Release and recovery

1. Stage first in Documents-owned MongoDB, recording declarations, expected version, actor, scope and a server-selected opaque key unique to that attempt. Replaying the same scoped actor and command ID with identical declarations returns the original upload; changed declarations conflict. PUT counts bytes against the exact declared size and hard cap, even when headers lie. Only a complete bounded body and a live MongoDB write claim may reach a single S3 create-only PUT (`If-None-Match: *`); retry must never replace bytes. No browser storage access, multipart upload or client-selected keys.
2. Before publishing, Documents reads that immutable object, counts its actual bytes, recomputes SHA-256 and validates PDF structure with bounded work. A client MIME header, storage metadata, ETag or `%PDF` prefix alone is not evidence. Fail closed on mismatch, invalid PDF or unavailable verification; PDF validation is not a malware clearance.
3. In one MongoDB atomic operation, require a live, unclaimed upload and matching expected current version, record the immutable release and its audit record, advance the current pointer, and save the finalize result. A still-authorized retry for the same actor and upload ID returns that original result even after expiry or supersession; concurrent replacements at the same expected version cannot both win. Never overwrite a prior release. S3 and MongoDB do not share a transaction.
4. Cleanup atomically marks an expired, never-released upload terminal before deleting just its exact known key. This excludes new PUT claims and competes with finalize on the same state; no released upload can enter cleanup. Wait out live write claims. A claim's timeout does not prove S3 stopped: keep a tombstone and retry/reconcile ambiguous PUT or delete outcomes, including a late object after an earlier miss. Never reuse keys or delete based on an S3 listing, blanket lifecycle rule, or absence of metadata. On restore or inconsistent metadata, stop cleanup until references are reconciled.

**Proposed preview bounds, not retention policy:** 1–1,048,576 bytes per upload, 15 minutes to upload/finalize, 60 seconds for a download grant, and at most 100 candidates (including retries) per five-minute cleanup pass. Bound request time and concurrent stages per scope. Keep released versions and audit for the life of the disposable synthetic environment; only abandoned uploads are reclaimed automatically. For later policy review, preserving releases by default simplifies NovaMotion's historical corrections but grows storage; authorized scheduled disposal with explicit holds and a separate audit-retention rule can limit the consultancy's exposure but makes old versions unavailable. Neither retention periods nor production deletion, legal holds, or audit access policy are decided here.

## Storage and compatibility

There is no pinned S3 server or SDK. These are **unqualified candidates**, not deployment or license decisions:

| Candidate | Upstream evidence and remaining limits |
|---|---|
| [SeaweedFS 4.55](https://github.com/seaweedfs/seaweedfs/releases/tag/4.55) | A [tagged integration test](https://github.com/seaweedfs/seaweedfs/blob/4.55/test/s3/distributed_lock/distributed_lock_test.go#L24-L138) reports one winner and an immediate read of its bytes when racing create-only writes. Do not extrapolate to multi-filer failover ([open upstream issue](https://github.com/seaweedfs/seaweedfs/issues/12842)). [Stock DELETE logging](https://github.com/seaweedfs/seaweedfs/blob/4.55/weed/s3api/s3api_object_handlers_delete.go#L223-L227) includes raw object keys; a supported redaction setup and applicable-advisory review are needed. |
| [RustFS 1.0.7](https://github.com/rustfs/rustfs/releases/tag/1.0.7) | Upstream tests [concurrent single-winner PUT](https://github.com/rustfs/rustfs/blob/1.0.7/crates/e2e_test/src/cluster_concurrency_test.rs#L148-L204) and [policy denial of unconditional PUT](https://github.com/rustfs/rustfs/blob/1.0.7/crates/e2e_test/src/conditional_write_policy_test.rs#L120-L196). This does not validate the chosen artifact, storage configuration or log redaction. |

Qualify the exact server and client pair for private authenticated PUT/GET/DELETE, permission denials, concurrent create-only writes, completed-write visibility, timeout/retry behavior and log redaction. Review the exact digest, bundled licenses/notices, SBOM, reachable advisories, architectures and support window; do not infer compliance from a source repository license or upstream scan. If immutability, private ingress or redaction cannot be proven, defer rather than use a public bucket, overwrite-capable fallback or raw storage logs.

New opt-in routes and Documents-owned data only; no existing record backfill, API change or broker event. Keep storage locators internal so the backend can be replaced without changing document/version IDs. Before a later migration, verify byte counts and hashes for all releases and restore metadata and objects together; disable ingress and cleanup on rollback without deleting releases. Any later durable process-history event needs a reviewed versioned contract and a local outbox committed with its owning write.

## Acceptance before implementation can be called verified

- Stage a known small synthetic PDF with independently fixed length and SHA-256, PUT it, finalize, then mint and redeem for version 1. Compare downloaded bytes as well as reported fields. Interrupt a replacement PUT; the current pointer and version 1 bytes remain unchanged. Release a second valid PDF, then read both exact versions. Lose the first finalize response and retry, including after supersession: the original result returns and the version count does not grow.
- Reject oversized, short, wrong-hash and non-PDF bodies (including a fake PDF header with matching length and checksum); no release or pointer advance. Reject a second PUT from changing stored bytes. Deny a token for the wrong audience, missing explicit grants, same-tenant wrong organization, other tenant, out-of-scope entity, a copied grant used by another actor, and grants expired or no longer authorized at redeem. A staged upload is never downloadable. Verify denied responses and logs expose no bytes, foreign entity existence, storage locator or grant.
- Race finalize against cleanup and a competing replacement; interrupt after the object write but before MongoDB commits, and after cleanup marks an upload but before deletion. After restart, prove one release at most per upload, old releases still readable, and only abandoned keys reclaimed in bounded retryable batches. Inject a late PUT and unavailable storage; neither permits deletion of a released object or publication of unverifiable bytes.

The smallest falsifier is an interrupted replacement that changes version 1, or a verified release whose object can be overwritten or reaped. Maintainer review under the [RFC process](../../GOVERNANCE.md#rfc-process) should involve Documents, security/licensing and the fulfillment owner before recording a decision. Defer shipment linking until the owning snapshot contract exists; defer the preview itself if the storage or isolation tests fail.
