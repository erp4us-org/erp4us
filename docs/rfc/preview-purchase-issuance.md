# Issue and receive local NovaMotion purchase orders

**Design for the confirmed [#23 preview direction](https://github.com/erp4us-org/erp4us/issues/23#issuecomment-7237683084).** This is a synthetic, local purchase record and physical receipt workflow; there is no supplier transmission, email, payment, or budget-balance reservation. The [budget approval design](preview-budget-approvals.md) precedes issuance. See the [HTTP contract](../../contracts/openapi/procurement-v1.yaml) for the implemented issuance boundary; the receipt section below is still a proposal.

## Procurement owns issuance

The separate `POST /v1/procurement/proposals/by-plan/{plan_id}/purchase-orders` requires both `procurement.purchase-order.issue` and `procurement.purchase-order.read`. A scoped `GET` needs only the read grant and works independently of the configured policy. The verified issuing actor may not be the preparer of the reviewed terms. The command names a nonzero `command_id` and the exact approved terms and policy identifiers and revisions; it cannot supply prices, quantities, recipients, actors, or authority. Recompute the current approval state from valid persisted decisions against the entire EUR draft, before grouping by supplier. The command must reject absent, incompatible or stale policy, missing stage, stale terms, or wrong scope. A prior approval or browser control is not authority to issue.

Persist one immutable **issuance batch per scoped plan**. Its child purchase order for each verified supplier holds the original supplier snapshot, positive immutable `EA` lines, exact quantity, exact price and amount, assigned order/line IDs, draft version, actor and creation time. Child totals must sum exactly to the approved draft total. Grouping does not change the budget result; splitting a draft across suppliers is not a way to satisfy a lower threshold. The batch and its idempotency receipt are one local Procurement transaction. Use the existing scoped write guard shared with terms edits and approvals: reread the exact latest revision and complete decisions after acquiring it, and reject edits once the batch exists. An original authorized retry returns the original IDs, while a second action or changed intent cannot issue the plan again. Corrections/cancellations are separate later work, not destructive changes to an issued record.

Illustrative preview: the saved five-line NovaMotion purchase draft totals `1882.40` EUR. If all five terms use the same supplier, an explicit authorized issue creates one purchase order with five lines, not five orders. If two suppliers were approved on the draft, it creates two child orders but still uses the same approved total. A fully covered reservation has no shortage proposal and never enters this path.

## Inventory owns receipt and allocation (proposed)

The [Procurement](../../contracts/openapi/procurement-v1.yaml) and [Inventory](../../contracts/openapi/inventory-v1.yaml) receipt operations and the [messaging contract](../specifications/nats-messaging.md#proposed-inventory-purchase-receipt-posted-v1) are proposed only. Existing issuance, material-plan reads and handoff are unchanged. This is the local [PUR-001](../requirements/catalog/PUR.yaml) / [INV-001](../requirements/catalog/INV.yaml) waiting-plan case, not general receiving.

### Discover and verify the issued source

`GET /v1/procurement/proposals/by-plan/{plan_id}/purchase-orders/receipt-source` selects the single issued batch by verified tenant, organization and plan ID. It returns only the plan ID and 1–32 immutable tuples unique by purchase order ID and purchase line ID, each with SKU, revision (including explicit null), `EA` and exact ordered pieces. From an authorized plan view the receiver can use this GET to choose a tuple without asking the buyer for IDs or getting the commercial purchase-order read grant. There is no wider search, cost, supplier, approver, internal audit or receipt status data. Neither a draft nor a foreign batch is visible through this read.

Both discovery and Inventory's new-command verification use the receiver's verified identity, exact scope and purpose-limited `procurement.purchase-order.receipt-source.read` grant. Proposed separation check: compare the receiver's stable actor ID against the saved terms preparer, all persisted approvers for the issued batch, and its issuer. Procurement enforces this against its private issuance audit; Inventory never receives those identities. Inventory calls the configured Procurement owner with a bearer credential valid for Procurement that verifies the same actor and selected scope. It must not substitute a broad service credential, trust actor headers, weaken audience checking, or use a browser-provided copy of the source. Activation requires confirming that same-actor credential binding in the local identity setup.

### Post and read allocation

`POST /v1/inventory/reservations/{order_id}/{line_id}/material-plan/purchase-orders/{purchase_order_id}/lines/{purchase_line_id}/receipts` takes `{ "receipt_id": "<uuid>", "pieces": "6" }`. Inventory verifies `inventory.purchase-receipt.post`, then for a new receipt looks up the plan by exact scoped **Sales** order and line. It uses the stored plan ID to request the owner source and independently matches exactly one tuple by **both** purchase IDs. Missing plans/batches and unmatched or foreign tuples are indistinguishable from absence (`404` within the authorized scope). Denied grants or receiver separation fail with `403`; a malformed, inconsistent or unavailable owner response or unverifiable destination fails closed with `503`. Inventory selects a verified component stock mapping at its recorded plan warehouse: no supplied warehouse, implicit default, free-stock fallback or supplier transmission. Quantities are exact canonical whole `EA` strings, positive `1`–`1000000` per receipt; zero is only a possible remaining quantity.

In one local transaction, recheck the command ID, purchase line's remaining balance and the linked plan row's eligibility against concurrent writes. The stored plan ID, SKU, revision and `EA` must match the issued source and its original positive buy row; the row must still be waiting, must have room for the **entire** allocation, and must not have closed, been released or entered an incompatible transition. Enforce one purchase line binding per buy row in this preview. For a new receipt against a verified line, reject a quantity above the order balance as `over_receipt` even if the row has also closed. Otherwise reject an ineligible plan, row or binding as `plan_ineligible`. A stock movement increases physical on-hand and the whole receipt is held for that row, not made available to another demand. Commit the immutable receipt and intent, movement, allocation/hold, updated line balance and sequence, and receipt fact/outbox atomically. A `409` never posts a partial effect. No shared DB, remote write or distributed transaction.

The first successful post returns `201`. After checking current Inventory authorization, an identical retry by the original actor returns `200` with the unchanged receipt and allocation **as of its original commit**, before looking up plan eligibility or contacting Procurement. This does not perform a new source read or depend on its availability or grant. Deduplicate by `(tenant, organization, receipt_id)` and compare the bound Sales order/line, purchase order/line and quantity; different intent under the same ID is `409`, a different authorized actor reusing that ID is denied without returning the record. Recheck inside the transaction to cover concurrent retries. If the commit outcome is uncertain (`503`), retry the same command and ID; do not resubmit a physical lot with a new ID.

`GET` on the same Inventory path uses separate `inventory.purchase-receipt.read` for a single current local allocation snapshot after the first committed receipt binds the line. It needs no Procurement credential or commercial grant; before binding it returns `404`, not a guessed balance. Report receipt allocation, line open, plan-row hold and remaining shortage independently. These come from Inventory's receipt/allocation state and current holds, not rewrites of the original `GET …/material-plan` `reserved`/`uncovered` values or the original `material-plan.netted` fact. All proposed receipt HTTP operations return `Cache-Control: no-store` on success and omit private approval data.

The [browser fixture](../../ui/tests/purchase-receipt.spec.ts) keeps an unresolved receipt ID through navigation in the same verified browser session. A newer allocation is not confirmation of that specific lot. The fixture does not restore an unresolved intent across sign-out or a full reload; recover the original ID with an authorized operator rather than assign a new one to the same physical lot. Review and verify this recovery path before activation. Browser fixtures do not provision receiver rights or prove stock posting.

**Unresolved recovery choice:** a browser recovery record could retain an opaque command reference without retaining a token, but it cannot help after device or browser-storage loss and must never be treated as authorization. A durable Inventory-owned receiving draft created before post survives that loss and can be reopened by the same authorized actor; it adds a separate lifecycle and must not hold or move stock merely by existing. A narrowly authorized operator read of the exact receipt reference can help reconcile a committed lot but cannot prove that an absent record has no in-flight write. In every option, resolve the exact scoped receipt and intent or retry the original command; do not infer lot identity from a cumulative balance, generate a replacement ID for an unresolved lot, or use direct DB edits. No recovery interface, data retention rule or operator grant is selected here.

### Procurement observes committed receipts

Procurement uses its existing scoped `procurement.purchase-order.read` visibility for the separate `GET /v1/procurement/proposals/by-plan/{plan_id}/purchase-orders/{purchase_order_id}/lines/{purchase_line_id}/receipt-status`. A local projection matches receipts to that exact immutable issued line and computes `open = ordered − sum(committed pieces)` over its verified contiguous per-line receipt sequence. It does not feed back into Inventory's command checks. `observed` means the quantities are as of `through_receipt_sequence` at `projected_at` (Procurement projection time), not a current balance or a claim of catch-up. A silent in-flight tail may make nonzero open too high, even when the broker consumer looks caught up. No verified fact yet, a known gap, or unresolved integrity/reconciliation trouble returns `unknown` with null balances, sequence and time. Unavailable local view storage is `503`; an unreadable view is not zero. A receipt source read never depends on the projection.

An authorized operator can reconcile a gap by comparing against Inventory's committed receipt/outbox records and replaying the unchanged owner envelopes. Rebuild from retained verified facts or a verified backup, preserving scoped deduplication and applied sequence. The bounded stream is not an archive; if a needed fact has expired, only a verified backup or owner-authorized recovery preserving the original identity can fill it. Otherwise keep the affected status unknown after a known gap. No new recovery API, ordinary receiver replay privilege, blind resend with new IDs, or ledger rewrites. Any later corrections must use separate authorized compensating movements/facts.

### Acceptance and activation

**End plates:** the original plan requests 20, reserves 8 and records 12 uncovered; issuance orders 12 and changes no stock. Before any receipt Procurement's projection is unknown (the ordered quantity is still 12). Post 6: Inventory's held quantity is 14, the receipt allocation is 6 and both line open and plan shortage are 6. After the fact is observed Procurement shows received 6/open 6; replay returns the same receipt with no additional effects. Post another 6 under a new ID: held 20, receipt allocation 12, line open and shortage 0, and Procurement eventually shows 12 received/open 0. The original snapshot still says reserved 8/uncovered 12, and the original shortage fact still has a buy row of 12. A thirteenth plate, an unissued line and a row that is no longer waiting are counterexamples, not stock movements.

Runtime proof still needs two competing receipts, changed retry intent, missing grants, receiver separation, cross-tenant and cross-organization denies, source and broker outages, lost acknowledgement/restart, out-of-order delivery and gap reconciliation without duplicate movement or allocation. Confirm the exact actor separation/delegation mechanics and operational recovery authority before activation. No new service, deployed grants, supplier transmission, receipt corrections or production acceptance are implied by these contracts.

The test-only persistence proofs use separate, randomly named databases on a **dedicated disposable MongoDB replica set**, not the browser preview or an existing deployment. To run both against that isolated replica set:

```sh
export INVENTORY_RECEIPT_TEST_MONGO_URI='<dedicated replica-set URI>'
export PROCUREMENT_RECEIPT_TEST_MONGO_URI="$INVENTORY_RECEIPT_TEST_MONGO_URI"
cargo test --locked -p inventory mongo_competing_lots_and_rollback_keep_all_effects_atomic -- --ignored
cargo test --locked -p procurement mongo_persists_gaps_replay_conflicts_and_bounded_continuation -- --ignored
```

Inventory checks concurrent admission and all-or-none rollback. Procurement checks gap and replay behavior after reopening the store, rejecting a conflicting lot without advancing the last verified prefix, and bounded continuation. These do not test a deployed broker consumer, role grants, the cross-service request, or complete process recovery.

An optional transport proof passes the actual Inventory-committed receipt envelopes to Procurement using `erp4us-messaging` and isolated JetStream. For this proof only, use a dedicated replica set and an **empty, disposable JetStream instance** with no credentials or external exposure; set the dynamic loopback ports explicitly. Never point it at the ERP stack or a shared broker:

```sh
export RECEIPT_TRANSPORT_TEST_MONGO_PORT='<loopback port>'
export RECEIPT_TRANSPORT_TEST_NATS_PORT='<loopback port>'
cargo test --locked -p inventory receipt_transport_publish_committed_inventory_outbox -- --ignored &&
  cargo test --locked -p procurement receipt_transport_observe_inventory_facts_and_exact_replay -- --ignored
```

The producer fixture sends committed lots in reverse receipt order; the consumer fixture reopens its store during the gap, applies the contiguous prefix, and checks that an exact-body broker replay creates no second effect. It deletes only the marked test stream on success. Stop the disposable stack afterward. This does not prove deployed broker principals, automatic relay lifecycle, cross-service OIDC, or operator authority.
