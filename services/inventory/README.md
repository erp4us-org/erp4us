# Inventory: reserve a confirmed line

The local fixture adapter accepts one [confirmed stock line](../../contracts/fixtures/confirmed-stock-line-v1.json) on stdin. It implements the approved SC-05 partial allocation in [INV-001](../../docs/requirements/catalog/INV.yaml): ten EA requested, six available, four expected → six reserved and four outstanding. Expected receipts are never eligible. A reservation is neither permission to ship nor a purchase commitment.

Run from the repository root with Rust and Docker:

```sh
cargo build --locked -p inventory
python3 tests/integration/inventory.py
```

The example starts an isolated, disposable MongoDB replica set, provisions an Inventory-only account, seeds eligible stock and launches a fresh Inventory process for each confirmation. It also runs two competing orders against the same six units. No existing database or Sales service is needed.

**Fixture interface.** With no arguments, the one-shot executable reads a [v1 fixture](../../contracts/schemas/confirmed-stock-line-v1.json), prints `{"reserved":6,"outstanding":4}` after commit and exits. Quantities in this slice are positive whole pieces (`EA`). Only the local operator supplies `INVENTORY_MONGO_URI`, `INVENTORY_TENANT_ID` and `INVENTORY_ORGANIZATION_ID`; do not expose this fixture runner as a public ingress. Build the standalone image with `docker build -f services/inventory/Dockerfile .`.

**Persistence v1.** Inventory owns `inventory.balances` (available pieces by scope/warehouse/article/unit) and `inventory.reservations` (original allocation by scope/order/line). Compound document `_id`s enforce uniqueness. A replica-set transaction commits the decrement and reservation together. Repeating the same line returns the current allocation, even if availability has changed; a different item, warehouse or quantity under the same line key is rejected. A missing balance has zero eligible pieces. Stop the runner to roll back the adapter; retain its database to preserve allocations. Receipt processing and shortage publication are later slices.

**Cancel an existing line.** Submit the [cancellation fixture](../../contracts/fixtures/cancel-stock-line-v1.json) in the same trusted scope. Inventory derives the release from its own reservation: for ten requested and six reserved it returns `{"released":6}`, restores six available pieces and closes four outstanding. The original amounts, time and actor are retained in a cancellation record on the line. Retrying returns `{"released":0}`; retrying the original confirmation reports zero reserved and zero outstanding. Unknown lines are rejected rather than acknowledged, so the caller can retry out-of-order delivery after confirmation. No supplier commitment changes.

**Preview runtime.** [`compose.inventory.yaml`](../../compose.inventory.yaml) adds an Inventory-only MongoDB account, a read API and a separately deployed, tenant-filtered NATS consumer for the [Sales order confirmation](../../contracts/schemas/nats-sales-order-confirmed-v1.json). An explicit seed registers the two scoped catalog SKU/revision pairs in the preview finished-goods warehouse. `NM-1000` starts at zero and `NM-2000` at six, with an opening stock movement for the latter. Seed retries preserve existing availability. The `articleId` fixture keys and live catalog SKU/revision keys are distinct; neither crosses into another service's DB. The consumer persists its inbox alongside the reservation and eligible-stock decrement before acknowledging JetStream. Invalid messages store a quarantine reference without their bodies; an unknown stock mapping is retried before quarantine. The preview does not yet expose quarantine repair, a public receipt/cancellation API, or purchasing events.

**Material plan.** The scoped [planning API](../../contracts/openapi/inventory-v1.yaml) resolves the pinned Manufacturing tree and nets it against the warehouse in the recorded reservation. The explicit seed also records component opening stock, with positive changes recorded as opening movements. The plan, verified structure snapshot and component allocations are recorded in one local transaction. Available subassemblies suppress the corresponding child needs; overlapping branches share the remaining stock. The plan supports at most 256 component nodes up to 16 assembly levels and positive whole pieces with an aggregate ceiling of 1,000,000 per row. Partial and fully covered results are both valid. A missing configured component is an error, not a zero-stock assumption. Releasing a stored plan and replanning are not implemented; the trusted cancellation fixture rejects a line with an active material plan rather than orphaning its holds.

**Procurement handoff.** An explicitly authorized command captures positive leaf shortages in one [versioned event](../../contracts/schemas/nats-inventory-material-plan-netted-v1.json) on the stored plan. The separate NATS relay marks it published only after a broker acknowledgement. Procurement alone records its proposal. There is no supplier selection, purchase approval or order issuance in this handoff.
